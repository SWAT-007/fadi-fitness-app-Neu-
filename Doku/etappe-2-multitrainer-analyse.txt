Bestehender Register-Flow:

Datei: server/src/routes/auth.ts
Zeilen: 46-76
Code:
authRouter.post("/register", async (req, res) => {
  const email = normalizeEmail(req.body?.email);
  const password = normalizePassword(req.body?.password);
  const role = normalizeRole(req.body?.role);

  if (!email || !password || password.length < 6 || !role) {
    return res.status(400).json({ message: "Invalid request" });
  }

  if (role === "client") {
    return res.status(403).json({ message: "Client registration requires an invitation link" });
  }

  try {
    const passwordHash = await bcrypt.hash(password, 12);
    const user = await prisma.user.create({
      data: {
        email,
        passwordHash,
        role: roleToUserRole[role],
        fullName: fallbackFullNameFromEmail(email),
        ...(role === "trainer" && {
          trainerProfile: { create: {} },
        }),
      },
    });

Bewertung:
- Ja, Register legt fuer TRAINER bereits User + TrainerProfile an.
- Das ist konzeptionell wiederverwendbar.
- Fuer Admin-CRUD waere eine eigene Admin-Route sicherer als /auth/register,
  weil Admin-CRUD typischerweise mehr Felder, klare Berechtigungen und
  spaeter Update/Delete/Freigabe-Logik braucht.

Welche davon heute trainergefiltert sind?
- Praktisch alle echten Daten-Seiten, weil ihre Backend-Routen trainerId-
  basierte Ownership-Checks oder trainerId-where-Bedingungen verwenden.
- Ausnahmen sind nur reine Auth-/Logout-Faelle.

========================================================================
EINSCHAETZUNG
========================================================================

Komplexitaet:
- Mittel bis eher hoch
- Grund: trainerId-Filter sind breit verteilt
- Gesamtzahl der trainerId-Filter-Query-Stellen: 66
- Keine zentrale Scope-Schicht fuer TRAINER vs ADMIN

Sicherster Ansatz:
- Nicht nur ueber Middleware loesen
- Stattdessen zentrale Scope-Helper im Backend einfuehren, z.B.:
  - resolveAccessScope(user)
  - resolveTrainerScope(userId, role)
  - Hilfsfunktionen fuer optionalen trainerId-Filter

Warum?
- Middleware kennt nur die Rolle
- Aber die eigentliche Daten-Sichtbarkeit entsteht in den Prisma-Queries
- Genau diese Queries muessen fuer ADMIN global und fuer TRAINER scoped bleiben

========================================================================
EMPFOHLENE REIHENFOLGE DER AENDERUNGEN
========================================================================

1. Zentrale Scope-Helfer bauen
   - ADMIN => global
   - TRAINER => trainerProfile.id

2. Trainer-Dashboard umbauen
   - entweder bestehende Route mit Role-Verzweigung
   - oder neue Admin-Dashboard-Route

3. clients.ts zuerst umbauen
   - hier sitzt bereits die meiste Ownership-Logik
   - resolveTrainerProfile/resolveOwnedClientProfile koennen erweitert werden

4. plans.ts und nutrition.ts anpassen
   - viele Listen/Details/Assignments haengen direkt an trainerId

5. notifications.ts und clientLinkTokens.ts nachziehen

6. Neues Trainer-CRUD Backend fuer ADMIN
   - Trainer erstellen
   - Trainer listen
   - Trainer bearbeiten
   - optional deaktivieren/loeschen

7. Frontend/Admin-Seiten erweitern
   - Admin-Dashboard
   - Trainer-Verwaltung
   - Bestehende Seiten fuer globale Admin-Sicht absichern

========================================================================
KURZFAZIT
========================================================================

Etappe 2 ist kein kleiner Role-Check-Umbau, sondern ein Scope-Umbau:
- TRAINER bleibt trainergebunden
- ADMIN muss global lesen koennen
- Das sollte ueber zentrale Scope-Helfer plus gezielte Query-Anpassungen
  umgesetzt werden, nicht nur ueber einzelne Inline-Checks.
